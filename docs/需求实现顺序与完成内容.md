# 需求实现顺序与完成内容（执行版）

> 更新时间：2026-04-23  
> 适用范围：基于 `docs/毕设当前阶段需求清单.md`（含“竞赛负责人设计（新增）”）

## 1. 文档目标

- 把需求拆成可执行阶段
- 明确每阶段完成内容与验收标准
- 明确阶段依赖，减少返工

---

## 2. 总体实施策略

- 先完成当前阶段主线（注册分流、教师审核、用户管理、队伍与页面优化）
- 再实施竞赛负责人机制（避免并行改动过多导致复杂度上升）
- 先数据库与后端，再前端联调

---

## 3. 阶段划分与顺序

## 阶段 A：当前阶段需求（不含竞赛负责人落地）

### A1. 注册与用户模型调整（最高优先级）

完成内容：
- 注册支持身份选择：学生/教师
- 注册流程分流：
  - 学生注册后直接可用
  - 教师注册后进入待审核
- 用户字段设计统一：
  - `username`：唯一登录账号
  - `displayName`：展示名（可重复）
- 个人信息支持修改：
  - 用户名
  - 邮箱

新增约定（学号/工号，防遗忘）：
- 当前阶段采用“最小实现策略”：
  - `account_no` 暂时复用 `username`
  - 注册时不单独采集学号/工号
  - 页面可继续按角色显示“学号/工号”标签，但值为 `account_no`
- 后续若要严格区分学号/工号，再单开迭代：
  - 学生注册采集学号
  - 教师注册采集工号
  - 对 `account_no` 做格式与唯一性校验

验收标准：
- 学生注册后可直接登录并使用
- 教师注册后未审核前无法进入正常教师功能
- 用户名重复时有明确错误提示
- 个人信息页可修改用户名/邮箱并持久化成功

---

### A2. 管理员端：教师注册审核 + 用户管理

完成内容：
- 新增/完善“教师申请审核”页面
- 支持审核通过/拒绝
- 新增/完善“用户管理”页面：
  - 用户列表
  - 用户详情
  - 修改用户信息
- 用户状态规则统一：
  - 页面统一使用“用户状态”命名（替代“审核状态”文案）
  - 用户状态与账号可用性绑定：
    - `APPROVED`：可登录使用
    - `REJECTED`：不可登录
    - `PENDING`：待审核，不可登录
  - 用户管理页编辑可设置用户状态，但仅允许设置为 `APPROVED` 或 `REJECTED`（不允许改为 `PENDING`）

验收标准：
- 管理员可完整走通教师审核流程
- 审核结果即时影响教师账号可用状态
- 管理员可查询并编辑用户资料
- 用户管理页修改用户状态后，列表/详情展示与后端状态保持一致
- 当用户状态为 `REJECTED` 时，账号登录被拦截且有明确提示

---

### A3. 教师创建队伍申请模块调整

完成内容：
- 文案统一：`教师申请` -> `创建队伍申请`
- 支持教师对同一竞赛发起多个申请
- 删除竞赛详情页“提交教师申请”按钮（改为新入口流程）

验收标准：
- 同一教师可对同一竞赛创建多条申请记录
- 页面文案不再出现旧命名

实现进展（2026-04-22）：

  - 竞赛详情页“提交教师申请”按钮已删除。
  - 主流程页面文案已统一为“创建队伍申请”。
- 未实现（新增待办）：
  - 新入口流程页未落地（当前仅移除旧入口，尚未提供“按竞赛发起创建队伍申请”的独立入口页）。
  - 仍有历史页面文件残留旧命名文案（非主路由）：`TeacherApplyCreate.vue`、`TeacherApplyList.vue`、`AdminTeacherApplications.vue`。

### A4. 竞赛模块行为调整

完成内容：
- 推荐逻辑仅返回“未开始（UPCOMING）”竞赛
- 报名按钮行为区分：
  - 学生：跳转竞赛详情
  - 教师：触发创建队伍申请
- 竞赛列表“算法模式”页面交互调整：
  - 不展示关键词、状态、重置控件
  - 普通提示不常驻，仅在 fallback 生效时展示提示条

验收标准：
- 推荐结果不出现进行中/已结束竞赛
- 不同角色报名按钮行为正确
- 算法模式页面无无效检索控件
- fallback 未生效时不出现提示条，生效时提示条正常显示

未完成（新增待办，2026-04-23）：
- 竞赛详情页字段顺序调整：`竞赛状态` 与 `竞赛ID` 位置互换。
- 竞赛详情页字段替换：`竞赛ID` 调整为 `报名截止时间`。
- 报名时效逻辑增强（待确认后实现）：
  - 当时间超过报名截止时间时，队伍自动从 `招募中` 切换为 `停止招募`。
  - 学生点击申请时，若队伍为 `停止招募`，弹出提示并阻止申请。
  - 先核对现有报名逻辑是否已部分覆盖，再确定改动范围与实现方案。

### A5. 队伍模块权限与交互优化

完成内容：
- 管理员权限收缩：仅保留“解散队伍”
- 队伍状态支持双向流转：`招募中 <-> 停止招募`
- 页面文案优化：
  - `成员管理` -> `成员信息`
  - 成员详情返回队伍详情页

验收标准：
- 管理员不能执行“解散队伍”之外的队伍管理动作
- 队伍状态可按需求双向切换
- 页面跳转与文案符合新规范

实现进展（2026-04-23）：
- 已实现：
  - 管理员权限收缩为仅保留“解散队伍”（不再执行停止招募、移除成员等操作）。
  - 队伍状态支持双向流转：`RECRUITING <-> CLOSED`。
  - 队伍详情文案由“成员管理”调整为“成员信息”，成员页返回队伍详情页。
- 当前结论：A5 可按已完成项管理。

## 阶段 B：竞赛负责人机制（A 阶段稳定后实施）

### B2. 负责人审核主流程

完成内容：

验收标准：
- 常规单据进入负责人审核链路
- 负责人越权审核被拦截
- 自审场景被正确阻止

## 5. 风险与控制

- 风险：数据库结构变更后服务启动失败（当前为 `ddl-auto: validate`）
  - 控制：先执行数据库迁移，再启动服务
- 风险：审核权限改动导致越权/漏权
  - 控制：接口增加“角色 + 竞赛归属”双重校验
- 风险：学号/工号需求在中期被遗忘
  - 控制：A1 固化“account_no 暂复用 username”策略，并在后续单独立项
- 风险：文案修改不一致
  - 控制：统一检索替换后做页面巡检
