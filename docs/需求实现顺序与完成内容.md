## 阶段 A：当前阶段需求（不含竞赛负责人落地）

### A1. 注册与用户模型调整（最高优先级）

完成内容：
- 注册支持身份选择：学生/教师
- 注册流程分流：
  - 学生注册后直接可用
  - 教师注册后进入待审核
- 用户字段设计统一：
  - `username`：唯一登录账号
  - `displayName`：展示名（可重复）
- 个人信息支持修改：
  - 用户名
  - 邮箱

新增约定（学号/工号，防遗忘）：
- 当前阶段采用“最小实现策略”：
  - `account_no` 暂时复用 `username`
  - 注册时不单独采集学号/工号
  - 页面可继续按角色显示“学号/工号”标签，但值为 `account_no`
- 后续若要严格区分学号/工号，再单开迭代：
  - 学生注册采集学号
  - 教师注册采集工号
  - 对 `account_no` 做格式与唯一性校验

验收标准：
- 学生注册后可直接登录并使用
- 教师注册后未审核前无法进入正常教师功能
- 用户名重复时有明确错误提示
- 个人信息页可修改用户名/邮箱并持久化成功

### A2. 管理员端：教师注册审核 + 用户管理

完成内容：
- 新增/完善“教师申请审核”页面
- 支持审核通过/拒绝
- 新增/完善“用户管理”页面：
  - 用户列表
  - 用户详情
  - 修改用户信息
- 用户状态规则统一：
  - 页面统一使用“用户状态”命名（替代“审核状态”文案）
  - 用户状态与账号可用性绑定：
    - `APPROVED`：可登录使用
    - `REJECTED`：不可登录
    - `PENDING`：待审核，不可登录
  - 用户管理页编辑可设置用户状态，但仅允许设置为 `APPROVED` 或 `REJECTED`（不允许改为 `PENDING`）

验收标准：
- 管理员可完整走通教师审核流程
- 审核结果即时影响教师账号可用状态
- 管理员可查询并编辑用户资料
- 用户管理页修改用户状态后，列表/详情展示与后端状态保持一致
- 当用户状态为 `REJECTED` 时，账号登录被拦截且有明确提示

## 5. 风险与控制

- 风险：数据库结构变更后服务启动失败（当前为 `ddl-auto: validate`）
  - 控制：先执行数据库迁移，再启动服务
- 风险：审核权限改动导致越权/漏权
  - 控制：接口增加“角色 + 竞赛归属”双重校验
- 风险：学号/工号需求在中期被遗忘
  - 控制：A1 固化“account_no 暂复用 username”策略，并在后续单独立项
- 风险：文案修改不一致
  - 控制：统一检索替换后做页面巡检
